# velari-harness glossary

Shared vocabulary for the plan documents in [plan/](plan/plan.md). Each term is defined here once; the plan documents link to this file instead of repeating the definitions. The **Status** column in the component table says what exists in the code today.

## Harness vocabulary

| Term | Definition |
|---|---|
| **Harness** | The container for one measurement: it binds a **Task** (cases plus scoring), a **Candidate** (the system under test) and scorers, and its `run()` chains the steps: run the candidate on every input, score each successful trial, package the records as a **Result**. In the finished kernel it also runs under an **Environment** (seed, limits, working directory), for N trials, reproducibly |
| **Candidate** | The thing a harness runs and measures, such as an agent, a model, a pipeline, a function or a customer's application. See the [component glossary](#component-glossary) |
| **Trial** | One attempt at one case, with its own derived seed |
| **Run** | One call to `Harness.run()`: every case and trial for one task and one candidate |
| **Run-and-judge harness** | The sense of "harness" used here (Inspect AI, lm-evaluation-harness, HELM, openai/evals, MLE-bench): run a candidate over cases in a controlled environment, record everything, score and aggregate, repeatably |
| **Agent harness** | The scaffold around a model: loop, tools, context handoff, persisted state, end-to-end verification (Anthropic's long-running agents harness). Not built; kept out of the core as a possible `agent-runtime` category |
| **Pipeline** | Ordered units of work, artifacts and lineage (Kedro, ZenML, Metaflow, Dagster). Not a harness; used only to prepare cases inside a task |

### Layers

| Layer | Name | What it is |
|---|---|---|
| L0 | Core kernel | Harness-agnostic. Knows nothing about LLMs or scikit-learn. Stage 2 |
| L1 | Categories | Bind the core's generic slots to a domain (see below) |
| L2 | Applied harnesses | Ready-made definitions per use case, registered by name and built from config |
| L3 | Runtimes and reporting | Where and how trials execute and where results go. Runtime extras such as `velari-harness[ray]` belong here |

### Categories (L1)

| Category | Candidate | Cases | Scorers | Trials |
|---|---|---|---|---|
| **Evaluation** | An agent, gateway call or retriever | Prompts, conversations, documents | Heuristics, similarity, LLM judges | Epochs or pass@k |
| **Data science** (`experiment`) | A model driver, fit/predict pipeline, or a data science agent | Data partitions, folds, competitions | Metrics | Seeds |
| **Agent runtime** (deferred) | A multi-session agent with persisted state | Tasks with a feature list | End-to-end verification | Sessions |

## Component glossary

Each row defines one concept: what it is, what it is not, a **core example** (generic, uses only L0) and an **applied example** (what the evaluation and data science categories layer on top in stages 3 and 4). The running example is *classify a support ticket's priority*: in the core it is a plain rule-based function; the applied rows swap in an agent (evaluation) and a clustering driver (data science).

Core examples are what stage 2 ships and tests. Applied examples are sentences, not code, and show what the next stages add.

| Component | Status | Definition | Core example | Applied example (layered on top) | Where |
|---|---|---|---|---|---|
| **Case** | Planned | One unit of work, split by who may see what: candidate-visible `input` and `files`, grader-only `target` and `grader_files`, plus `metadata` (split, tags). `id` defaults to a hash of the content. Data only; it knows nothing about who will run it | `Case(input="Card was charged twice", target="high")` | Evaluation: input is a user message, target a reference answer or expected tool call. Data science: input and files are the data the agent works on; target and grader files are the hidden test labels | `schemas/case.py` |
| **CaseView** | Planned | What the candidate receives for a case: id, input, files, metadata. Never the target or grader files, so a candidate cannot read the answer | `case.view()` has no `target` attribute | Evaluation: the user message and attached documents. Data science: the training data, never the test labels | `schemas/case.py` |
| **Dataset** | Planned | An ordered, filterable collection of cases with a stable order, so a run can be repeated and sliced. Its `fingerprint` (a hash of ids and inputs) is stored in the Result, so a run says which data it used. Not a loader: sources are adapted into it | `Dataset.from_frame(df_tickets, input="text", target="priority")` | Evaluation: built from the `examples/ai/evals` data. Data science: one case per fold from `DataPartition`, or one per competition | `schemas/case.py` |
| **Output** | Planned | What a candidate returned for one case: a value, any files it produced (`artifacts`, name to path), usage, latency and the raw payload. Not a judgement | `Output(value="high", latency_sec=0.001)` | Evaluation: `AgentResponseInfo` mapped in, with token usage and tool calls. Data science: a submission CSV in `artifacts`, plus fit time | `schemas/output.py` |
| **Score** | Implemented (minimal) | One scorer's verdict. As built it is a plain `float` in `TrialRecord.scores`, keyed by scorer name, `None` when the scorer raised (an invalid score is not a zero). A richer `Score` object (a `passed` threshold, a label, a `valid` flag and `error`) is planned for when a scorer needs it | `{"email_match": 1.0}` | Evaluation: an LLM judge's grade, `None` when the judge call is rate limited. Data science: adjusted Rand index | `schemas/response/record.py` (`TrialRecord.scores`) |
| **TrialRecord / Event** | Implemented (minimal) | The complete, immutable record of one attempt at one case: seed, status, attempts, whether it was scored and valid, output, artifacts location, scores, error and timestamped events. The unit that is saved, re-scored and audited. As built in increment 3, `TrialRecord` holds the input's position (`index`), the `input`, `status` (`success` or `error`), `output`, `error` and `duration_sec`; seed, attempts, scored and valid flags, artifacts and events come later | `TrialRecord` for case `T-1042`, trial 0, seed 913, status success, attempts 1 | Evaluation: events hold each model and tool call. Data science: events hold fit and predict steps, or each draft and debug step of an agent | `schemas/response/record.py` |
| **Candidate** | Implemented (generic input and output) | The thing the harness runs and measures: anything that takes an input and returns an output, such as an agent, an LLM gateway call, a retriever, a model driver, a plain function or a customer's application. It has a per-trial lifecycle: `setup(ctx)`, `run(view, ctx) -> Output`, `teardown(ctx)`, and teardown always runs, even after a failed run. It is chosen at run time and never baked into a task, so one task can compare several candidates (a baseline and a variant). It is not the harness (which runs it), not the scorer (which judges it) and not the task (what is measured). As built in increment 2, `run(input) -> output` takes and returns any value; the typed `CaseView`, `Output` and `TrialContext` arrive in later increments | `CallableCandidate(rule_based_priority)` (setup and teardown do nothing) | Evaluation: an `Agent` or `LLMGateway` adapter. Data science: a `ModelDriver` adapter (seeded fit and predict), or an agent that writes a submission | `protocols/candidate.py` |
| **TrialContext** | Planned | The per-trial facilities handed to a candidate: the derived `seed`, a private `workdir`, the `sandbox`, and `emit(name, data)` to record events. Not global state | `ctx.emit("rule_matched", {"rule": "refund"})` | Evaluation: model turns and tool calls as events. Data science: fit and predict steps | `protocols/candidate.py` |
| **Sandbox** | Planned | Where a candidate executes: `start`, `exec`, `upload`, `download`, `stop`. The single seam for isolation. Not the Environment, which holds conditions rather than a place | `LocalSandbox`: a per-trial working directory on the local machine | Evaluation: sandboxed tool execution. Data science: a Docker container with a GPU, or a Daytona or Modal sandbox, as L3 runtimes (stage 6) | `protocols/sandbox.py`, `execution/sandbox.py` |
| **Scorer** | Implemented (minimal) | A judge of one output: `score(view, reference, output) -> Score`. As built it is a plain function `fn(output, reference)` returning a number (a `bool` counts as 1.0 or 0.0), named by its `__name__`, so the functions in `velari_ai.ai.evals` such as `exact_match` work as they are; the `Scorer` protocol is deferred until a scorer needs state or the input. It receives the case view, the grader-only reference (target and grader files) and the Output with artifact paths, never the live sandbox, so it can run again on stored records | `exact_match` comparing the output to the reference | Evaluation: heuristics from `ai/evals`, LLM-as-judge. Data science: metric functions from the sklearn `scoring.py`, or a grader that reads a submission CSV against hidden labels | `execution/runner.py` (applies them); a protocol in `protocols/scorer.py` is planned |
| **Task** | Implemented (minimal) | The declarative definition of *what is measured*: a dataset, scorers, optional preparation steps, a number of trials, a `version`, and a policy for missing or invalid scores (`exclude` or `zero`). Candidate-agnostic by design, so one task compares many candidates. As built in increments 4 and 8, a `Task` is an immutable `name`, a tuple of plain `inputs`, a `version` and optional `references` (the expected value per input, for scorers); the dataset of cases, scorers on the task itself, preparation steps, trials and the missing-score policy come later | `Task("ticket-priority", dataset, scorers=[ExactMatch()], trials=3, version="1")` | Evaluation: `support-agent-quality` with a judge scorer. Data science: `segment-clustering` with partition cases | `schemas/request/task.py` |
| **Environment** | Implemented (minimal) | The fixed conditions a run happens under, held the same for every candidate so that results can be compared and a run can be repeated: the seed, limits, how failures are treated, and what is pinned. Think of the controlled variables in an experiment: the candidate is what you change, the environment is what you keep constant. It is declarative data, not behavior; it is not the task, the candidate, the runtime, or the place the candidate runs (that is the Sandbox). See the [environment note](architecture/environment.md). As built in increment 5, an `Environment` is an immutable base `seed` (an int, checked) with `seed_for(key, trial)`, which derives a repeatable seed for each trial; the artifacts directory, limits, error and retry policies and fail-fast settings come later, and the Runner does not read it yet | `Environment(seed=42, fail_fast=False, max_error_ratio=0.2)` | Evaluation: adds token and cost limits. Data science: dataset snapshot and library versions | `schemas/request/environment.py` |
| **Metric / reducer** | Planned | A function that turns many scores into one number, skipping invalid scores. Reducers fold the trials of one case (mean, max, pass@k); metrics fold cases (mean, stderr) | `mean`, `stderr`; `pass_at_k(k=3)` over three trials | Evaluation: pass@k for agent success. Data science: mean ARI across seeds with a confidence interval | `results/metrics.py` |
| **Result** | Implemented (minimal) | Everything one run produced: a spec (resolved config, task version, dataset fingerprint, candidate name, limits actually applied), the status, all records and stats. Can be tabulated, summarised and re-scored. As built: the harness name, one `TrialRecord` per input in order, the duration, and computed `trials` (a count per status) and `scores` (the mean per scorer) | `result.summary()` gives `{"exact_match": {"mean": 0.83, "stderr": 0.04}}` | Evaluation: compare two prompt variants side by side. Data science: compare KMeans and HDBSCAN | `schemas/response/result.py` (data); how `to_frame()`, `summary()` and `rescore()` are provided is decided when they are added: methods on the model, or functions in `results/` |
| **Store** | Planned | Persists a `Result` and its artifacts and reads them back unchanged. Not a tracking server | `save(result, tmp_path / "run-001")`, then `load(...)` | Evaluation: attach to MLflow or Phoenix later. Data science: write beside the experiment outputs | `results/store.py` |
| **Limits** | Planned | Guards the runner enforces on any candidate: per-trial time, error budget, fail-fast. A candidate cannot opt out | `time_limit_sec=5` stops a hung trial and records `TIMEOUT` | Evaluation: adds token, message-count and cost limits. Data science: a fit timeout, a step budget | `execution/limits.py` |
| **ErrorPolicy / RetryPolicy** | Planned | Decides what a failed attempt means: for each exception type, retry or not, scored or not, valid or not; `RetryPolicy` sets the retry count and backoff. Timeouts get their own status | A `TimeoutError` is recorded as `TIMEOUT`, scored and valid; a `ConnectionError` is retried twice; any other error is `ERROR` and not scored | Evaluation: a rate-limited judge call is retried, and its score is invalid if retries run out. Data science: an out-of-memory fit is an error and not retried | `execution/limits.py` |
| **Runner** | Implemented (minimal) | The executor: for every case and trial, sequentially, it runs `setup`, `run` and `teardown`, collects artifacts, then applies the scorers. It enforces limits and the error policy and records failures instead of raising. With `score=False` it only produces records. Not a scheduler. As built in increment 3, it runs one candidate over a sequence of inputs, one trial per input and in order, with the candidate's lifecycle per trial, and returns a list of `TrialRecord`; there are no scorers, limits, repeated trials, artifacts or `score=False` yet | `Runner().run(task, candidate, env)` returns a `Result`; `score=False` returns records without scores | Evaluation: concurrent trials against a rate-limited API (stage 3). Data science: sequential fits with per-trial seeds | `execution/runner.py` |
| **HarnessConfig** | Implemented | The settings every harness shares: a name (the seed is not here; it belongs to the `Environment`). It is checked at construction (a non-string or empty name raises) and immutable. Category harnesses subclass it, as a frozen dataclass, to add fields. Built from OmegaConf; explicit overrides win over the config, which wins over defaults | `HarnessConfig.from_config(cfg, defaults={"name": "ticket-triage"})` | Evaluation: adds the judge model and number of trials. Data science: adds the number of folds | `execution/config.py` |
| **Harness** | Implemented (minimal) | The container for one measurement: a name, a config, a task, a candidate and optional scorers. `run()` returns a `Result` by chaining three steps, run the candidate on every input (the `Runner`), score each successful trial (`score()`, public so records can be scored again), and package the records. A failed trial is data in its record, so a run has no status of its own. It does not use an `Environment` yet. Build it with `Harness.for_task(task, candidate, scorers=[...])` | `Harness.for_task(task, candidate, scorers=[exact_match]).run()` | Evaluation: `agent-tool-accuracy` on `support-agent-quality`. Data science: KMeans and HDBSCAN on `segment-clustering` | `execution/harness.py` |
| **Registry** | Planned | A name-to-object table with `register`, `get` and `names`; errors on unknown or duplicate names. Lets configs and third parties refer to components by name | `scorers.register("exact_match")`, then `scorers.get("exact_match")` | Evaluation: `"llm_judge"` and `"tool_call_accuracy"` registered by the evaluation layer. Data science: `"kmeans"` and `"hdbscan"` | `registry/registry.py`, `registry/registries.py` |
| **Build (`from_config`)** | Planned | Builds a harness from an OmegaConf config plus explicit overrides; `None` means defaults. The only place configs become objects | `Harness.from_config(cfg, name="nightly-check")` | Evaluation: config group `harness/evaluation/*.yaml`. Data science: `harness/experiment/*.yaml` (stage 5) | `registry/build.py` |

### Naming note: Candidate

**Candidate** is the neutral name for whatever is being run and measured, so the same word works for an evaluation of an agent, a data science experiment, a customer's own harness and a runtime check. It reads naturally in comparisons ("run the task against the baseline and the new candidate").

Considered and not used: **Subject** (testing jargon that is unclear outside it, and was the original name), **Target** (already `Case.target`, the expected answer), **Model** and **Agent** (too narrow), **Runnable** (a LangChain term for a different concept), **SystemUnderTest** (precise but long), **Workload** (overlaps Task).
